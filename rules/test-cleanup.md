# Test Cleanup — FK-Safe Ordering

## The Rule

**Always use a single `cleanupTenantData()` helper for full tenant cleanup.** Do NOT write inline `deleteMany` chains in test files. Inline cleanup is the #1 source of flaky test failures when schema FK constraints change.

When you have N composite tenant FKs enforcing cross-tenant isolation at the DB level, **delete ordering is critical**. A wrong-order cleanup that worked before a schema change can silently break after new FKs are added.

---

## Canonical Delete Order

Define a single canonical delete order and put it in `testHelpers.ts` (or equivalent). **This is the single source of truth.** All tests delegate to this helper. The order follows the FK dependency graph from leaves to root:

```
Depth N (deepest leaves — child tables with no children of their own)
  ↓
Depth N-1 (intermediate children)
  ↓
...
  ↓
Depth 0 (root-adjacent tables that only reference the tenant root)
  ↓
Tenant root (e.g., Org)
```

Document this graph in a markdown file (this one). When a new model is added to the schema, add it to `cleanupTenantData()` at the correct depth AND update the graph documentation.

---

## SET NULL FKs: Silent Corruption Risk

Composite FKs that use `ON DELETE SET NULL` are dangerous. **Wrong cleanup ordering on these produces false-green tests** — the FK column is silently nullified instead of failing.

**RESTRICT FKs fail loudly** (safe). **SET NULL FKs fail silently** (dangerous).

Maintain a table in this file (or a similar canonical doc) listing every SET NULL FK in your schema and the risk if the parent is deleted before the child:

```
| Child.column          | Parent       | Risk if parent deleted first              |
|-----------------------|--------------|-------------------------------------------|
| ChildTable.parentId   | ParentTable  | Orphaned child loses context              |
| ...                   | ...          | ...                                       |
```

When you add a new SET NULL composite FK, add it to this table. The table is the audit trail.

## Composite FK Pattern (PostgreSQL)

Use composite FKs `(childId, tenantId) → parent(id, tenantId)` for DB-level defense against cross-tenant linkage. Prisma can't generate these — they need raw SQL migrations.

### Schema (Prisma)

Add `@@unique([id, tenantId])` to the parent model:

```prisma
model Parent {
  id       String @id @default(cuid())
  tenantId String
  // ... fields
  @@unique([id, tenantId])  // Required for composite FK reference
}
```

### Raw SQL Migration

```sql
-- For RESTRICT / CASCADE / NO ACTION:
ALTER TABLE "Child" ADD CONSTRAINT "Child_parentId_tenantId_tenant_fk"
  FOREIGN KEY ("parentId", "tenantId") REFERENCES "Parent"("id", "tenantId")
  ON DELETE <match existing FK action> ON UPDATE CASCADE;

-- For SET NULL: MUST use column-specific syntax (PostgreSQL 15+):
ALTER TABLE "Child" ADD CONSTRAINT "Child_parentId_tenantId_tenant_fk"
  FOREIGN KEY ("parentId", "tenantId") REFERENCES "Parent"("id", "tenantId")
  ON DELETE SET NULL ("parentId") ON UPDATE CASCADE;
```

### Critical Rules

- ON DELETE action MUST match the existing simple FK's action.
- **SET NULL FKs MUST use column-specific syntax** — never bare `SET NULL` on composite FKs. Bare SET NULL tries to null all referencing columns including non-nullable `tenantId`, causing NOT NULL violations. PostgreSQL 15+ syntax `ON DELETE SET NULL ("fkColumn")` nulls only the FK column.
- Use MATCH SIMPLE (PostgreSQL default) — nullable FK columns skip validation when NULL.
- Composite FKs are managed via raw SQL, **never auto-generated by Prisma**.
- `prisma migrate dev` may silently drop composite FKs — always verify after migration.
- New child models MUST include `tenantId` and a composite tenant FK.
- **Naming convention:** `{ChildTable}_{fkColumn}_tenantId_tenant_fk`

### Verification

After any schema migration, verify composite FKs are intact:

```sql
SELECT count(*) FROM pg_constraint
WHERE contype = 'f' AND conname LIKE '%_tenant_fk';
```

Track the expected count in your project docs. If the count drops after `prisma migrate dev`, the migration must be investigated — Prisma may have silently dropped raw SQL constraints.

## Rules

1. **Always use `cleanupTenantData()`** from `testHelpers.ts` for full tenant cleanup. Do NOT write inline `deleteMany` chains.
2. If you must clean up a subset, you MUST still respect the FK ordering above. Delete children before parents.
3. **When adding a new model:**
   - (a) Add `@@unique([id, tenantId])` if it's a parent
   - (b) Add a composite tenant FK via raw SQL migration
   - (c) Add to `cleanupTenantData()` at the correct depth
   - (d) Run `/check-tenancy --schema` to verify
4. **Partial cleanup is OK** if your test only creates a subset of tables. But the ordering of the subset must match the canonical order.

---

## When Inline Cleanup Is Acceptable

- Cleaning up a **single table** created within one `it()` block (no FK children)
- Cleaning up **leaf tables only** (no children)
- Test creates a narrow subset AND respects canonical FK ordering

---

## Schema Blast Radius

When the schema changes (new model, new FK, new constraint), these files may need updating:

- `testHelpers.ts` — `cleanupTenantData()` ordering
- Any inline cleanup in `*.db.test.ts` files
- This file (canonical ordering documentation)
- Any FK validation tests

Run a schema-blast-radius check after any schema change to catch ordering violations. A simple script that greps for `deleteMany` outside `testHelpers.ts` and flags the offenders is enough.

---

## Schema Change Checklist

When the schema changes (new model, new FK, altered FK action):

- [ ] Update `cleanupTenantData()` in `testHelpers.ts`
- [ ] Update the canonical delete order documentation
- [ ] If new SET NULL FK: add it to the SET NULL risk table
- [ ] Run DB-gated tests (`RUN_DB_TESTS=1`) to verify all cleanup works
- [ ] Verify composite FK count after migration (raw SQL query above)
- [ ] If count dropped: investigate. `prisma migrate dev` may have dropped raw SQL constraints.

---

## Common Mistakes

1. **Inline `deleteMany` in a beforeEach** — works today, breaks tomorrow when a new FK is added. Use `cleanupTenantData()`.
2. **Deleting the tenant root first** — composite FKs cascade or RESTRICT; this either takes everything with it or fails loudly. Always delete children first.
3. **Missing a new model from `cleanupTenantData()`** — tests pass in isolation but fail when run alongside other tests. Update the helper when you add a model.
4. **Bare `ON DELETE SET NULL` on a composite FK** — tries to null all referencing columns including non-nullable `tenantId`. Use column-specific syntax: `ON DELETE SET NULL ("fkColumn")`.
